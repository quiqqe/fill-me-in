**The problem we were fixing**

nginx doesn't run PHP itself. It forwards each PHP request to the PHP-FPM container, which it reaches by the hostname `php` on port 9000. In Docker, that name points to the container's internal IP address. When you recreate the `php` container (for example with `docker compose up -d --force-recreate php`, or after a rebuild), it usually gets a **new IP**.

nginx looks up `php` once, when it starts, and keeps using that IP. After a recreate it kept sending requests to the old address, where nothing was listening anymore. You got **502 Bad Gateway** errors until you reloaded or restarted nginx, which made it look up the name again.

**What the old config did**

It had `set $php_fpm php:9000;` and then `fastcgi_pass $php_fpm;`. Putting the address in a variable is an old trick that makes nginx look up the name at request time instead of only at startup. It works, but it's fragile. It needs a separate `resolver` line pointing at Docker's DNS server, it silently falls back to "look up once" if someone removes the variable, and it can't use a proper upstream block.

**What I changed it to**

```nginx
resolver 127.0.0.11 valid=1s;   # Docker's built-in DNS

upstream php_fpm {
    zone php_fpm 64k;           # shared memory nginx needs to store the IP it looks up
    server php:9000 resolve;    # keep checking this name for IP changes
}

# ...
fastcgi_pass php_fpm;
```

- **`upstream` + `resolve`**: this is the built-in way to tell nginx "this backend's IP can change, keep checking it." nginx re-checks the name in the background and switches to the new IP on its own.
- **`zone`**: `resolve` only works if the upstream has a shared memory zone. That's where nginx stores the current IP so all its worker processes see the update.
- **`valid=1s`**: nginx trusts a lookup for at most 1 second before checking again. After a recreate, nginx picks up the new IP within about a second.

**What this means for you**

You can recreate or rebuild the `php` container and the site keeps working. You no longer need to run `nginx -s reload` or restart nginx. At most, requests in the first second or so might fail while the new container starts.

One requirement: `resolve` in an `upstream` block needs nginx **1.27.3 or newer** (in older free versions it only existed in the paid NGINX Plus). If your nginx image is older, nginx will refuse to start with an error about `resolve`. Updating the image tag fixes that.

## The problem

nginx sits in front of your PHP container (PHP-FPM) and forwards PHP requests to it at the hostname `php`. When you recreate the `php` container, Docker usually gives it a new IP address.

By default, nginx looks up `php` once, at startup, and keeps using that IP until it's reloaded. So after you recreated the container, nginx kept sending requests to the old address, where nothing is listening anymore. Your site returned errors (typically 502 Bad Gateway) until someone ran `nginx -s reload` or restarted nginx.

## What I changed

**1. Removed `set $php_fpm ...`.** That was a common workaround. If you put the address in a variable (`set $php_fpm php:9000;` then `fastcgi_pass $php_fpm;`), nginx looks the name up again at request time instead of once at startup. It works, but it's a hack: you lose the normal upstream features, and it's easy to get subtly wrong.

**2. Replaced it with an `upstream` block** set up to re-resolve the name on its own:

```nginx
resolver 127.0.0.11 valid=1s;   # Docker's internal DNS; trust each answer for 1 second

upstream php_fpm {
    zone php_fpm 64k;            # shared memory so the resolved IP can be updated live
    server php:9000 resolve;     # keep re-looking-up "php" instead of only at startup
}

# ...
fastcgi_pass php_fpm;
```

- `resolve` tells nginx to keep checking what IP `php` points to while it runs.
- `zone` is required for `resolve`. It gives nginx a shared memory area where it can swap in the new IP without reloading.
- `valid=1s` means nginx trusts each DNS answer for only 1 second before asking again, so it notices a new IP almost immediately.

## What this means for you

You can now run something like `docker compose up -d --force-recreate php` and nginx picks up the new container by itself within about a second. You no longer need to reload or restart nginx afterward.

One requirement: `resolve` inside an `upstream` block needs open-source nginx 1.27.3 or newer (older versions only had it in the paid NGINX Plus). If your nginx image is older, it will refuse to start with an error about `resolve`. In that case, update the image (e.g. `nginx:stable` or `nginx:mainline`).
