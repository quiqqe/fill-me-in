In short: nginx used to lose track of your PHP container whenever that container was recreated, and you had to reload nginx to fix it. I changed the config so nginx finds the container again by itself.

## What was going wrong

nginx doesn't run PHP itself. It passes PHP requests to a separate service, PHP-FPM, which it reaches by a hostname like `php:9000`. In Docker that name maps to the container's IP address, and **a recreated container usually gets a new IP**.

By default, nginx looks up that name's IP only once, when it starts, and keeps using that address. So this happened:

1. nginx starts. `php` resolves to, say, `172.18.0.5`.
2. You recreate the php container (`docker compose up -d --force-recreate php`, a rebuild, etc.). It comes back as `172.18.0.7`.
3. nginx keeps sending requests to `172.18.0.5`, where nothing is listening. Your site returns **502 Bad Gateway**.
4. It stays broken until you reload nginx, which makes it look up the name again.

## What the old config did and what I changed

- **`set $php_fpm`**: the config stored the address in a variable. That's a common workaround: when the address is a variable, nginx looks the name up per request instead of once at startup. It's a hack with side effects, though. For example, you can't use features that need a defined backend group, like connection reuse. I removed it.
- **`upstream` block with `zone` + `resolve`**: this is the proper built-in way to do the same thing. An `upstream` block names the backend (your PHP container). `resolve` tells nginx to keep re-checking the hostname's IP while it runs. `zone` is a bit of shared memory nginx needs to store the updated address.
- **`valid=1s`**: this setting goes on the `resolver` line, which points nginx at Docker's internal DNS. It means "trust a DNS answer for only 1 second." So within about a second of the container getting a new IP, nginx picks it up.

## What this means for you

You can recreate or restart the php container whenever you like without touching nginx afterwards. To check it yourself, recreate the php container, then load a page. You should get a normal response, not a 502.

One requirement: `resolve` inside an `upstream` block needs nginx 1.27.3 or newer (older free versions only had it in the paid NGINX Plus). If nginx fails to start with an error about `resolve`, your nginx image is too old and needs updating.

## What was going wrong

- nginx passes PHP requests to the PHP-FPM container, which it finds by the hostname `php`.
- Docker gives a container a new IP address each time it's recreated (for example after `docker compose up --force-recreate php` or a new image).
- By default, nginx looks up `php` once, when it starts, and keeps using that IP. After a recreate, it kept sending requests to the old address, which no longer exists. The site returned **502 Bad Gateway** until someone ran `nginx -s reload`.

## What the old config did and why I removed it

The config had a common workaround:

```nginx
set $php_fpm php:9000;
fastcgi_pass $php_fpm;
```

Putting the address in a variable (`$php_fpm`) makes nginx look up the name on each request instead of once at startup. It works, but it's an indirect trick. It also gives up features of a proper backend definition, like keeping connections open between requests. I replaced it with the setup nginx provides for this case.

## What's there now

```nginx
resolver 127.0.0.11 valid=1s;   # Docker's built-in DNS; trust an answer for at most 1 second

upstream php_fpm {
    zone php_fpm 64k;            # shared memory for this backend group; nginx requires it for resolve
    server php:9000 resolve;     # keep re-checking what IP "php" points to
}

# in the location block:
fastcgi_pass php_fpm;
```

- **upstream**: a named group of backend servers, here just the PHP container.
- **resolve**: nginx keeps re-checking in the background which IP `php` points to, and switches to the new address when it changes.
- **zone**: a small block of shared memory where nginx stores the current address so all its worker processes use the same one.
- **valid=1s**: nginx trusts each DNS answer for at most one second. After a recreate, it picks up the new IP within about a second. Without this, it would use Docker DNS's own expiry time.

## What this means for you

You can recreate or restart the `php` container whenever you like. Expect a second or so of possible errors while it comes back up, then requests reach the new container without a reload.

One thing to check: open-source nginx only supports `resolve` inside `upstream` from version **1.27.3** (before that it was in the paid Nginx Plus only). Run `nginx -v` in the nginx container. On an older version, nginx will refuse to start with this config. In that case, either upgrade the image or I can put back the variable workaround.
