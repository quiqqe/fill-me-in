**Short version:** nginx used to lose track of your PHP container whenever it was recreated, and you had to reload nginx to fix it. I changed the config so nginx finds the container again by itself.

## What was going wrong

nginx passes PHP requests to a container called `php` on port 9000. To reach it, nginx has to turn the name `php` into an IP address, which Docker's built-in DNS provides.

By default, nginx looks up that name **once, at startup**, and keeps using that IP forever. When you recreate the `php` container (after a rebuild or `docker compose up` with changes), Docker usually gives it a **new IP**. nginx keeps sending requests to the old address, where nothing is listening, so your site returns **502 Bad Gateway** until you reload nginx and it looks up the name again.

## What the config had before

It used a common workaround:

```nginx
set $php_fpm php:9000;
fastcgi_pass $php_fpm;
```

When the address is stored in a variable, nginx looks up the name at request time instead of only at startup. It works, but it's a hack that bypasses nginx's normal way of defining backends. I replaced it with the officially supported approach.

## What it does now

```nginx
resolver 127.0.0.11 valid=1s;     # Docker's DNS; trust each answer for 1 second

upstream php_fpm {
    zone php_fpm 64k;             # shared memory, needed so the IP can update while running
    server php:9000 resolve;      # keep re-checking what "php" points to
}

fastcgi_pass php_fpm;
```

- **`upstream` block:** a named definition of "where PHP lives" that the rest of the config points to.
- **`resolve`:** tells nginx to keep looking up `php` while it runs, not just at startup.
- **`zone`:** a small piece of shared memory. Without it, nginx has nowhere to store an IP that changes while it's running, and `resolve` won't work.
- **`valid=1s`:** nginx treats each DNS answer as good for one second and then checks again. So within about a second of the container getting a new IP, nginx switches to it.

## What this means for you

You can recreate or restart the `php` container and the site comes back by itself, with no `nginx -s reload` needed. At most you might see an error for a second or so while the new container starts.

Two things to know:
- `resolve` inside an `upstream` block requires **nginx 1.27.3 or newer** (older free versions only had it in the paid NGINX Plus). On an older version, nginx will refuse to start and report an error on that line.
- To check that it works, recreate the PHP container (`docker compose up -d --force-recreate php`) and load a page. It should work without touching nginx.
